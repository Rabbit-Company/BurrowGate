# Custom Challenge Pages

BurrowGate serves an interactive verification page whenever a visitor must complete a browser challenge (for example the `pow-sha256` proof of work). **Each challenge provider owns its own default page**, tailored to what it actually renders - a form has no reason to show `pow-sha256`'s progress bar, and a canvas-based game gets a layout sized for its canvas instead of a generic status card. A site can override any provider's template independently, and can still keep one general customization that applies to any provider without its own explicit override.

Unlike custom error responses, a challenge page is always HTML: it has to run JavaScript to solve and submit the challenge, so there is no JSON mode.

## Configuring templates

Open the **Sites** tab, edit a site, and use the **Challenge page** editor. It shows one tab per challenge provider - select a tab to edit that provider's template; the textarea is pre-filled with whatever currently renders for it (its own saved override, or the resolved fallback below). Below the template textarea and the placeholder list, a **Text** section lists every visitor-facing string for that provider as its own labeled input, pre-filled the same way - see [Text](#text) below. Changes apply to new challenge flows immediately after the site is saved. **Reset to default** restores the _selected provider's own_ defaults - both the HTML template and every text field on that tab (not a single generic template); like the reset button elsewhere, it only changes the editor contents, so save the site to apply it. Clearing a tab's template entirely, or a single text field, and saving removes that override rather than storing an empty value.

### Resolution order

For a given site and the provider active on the current step, most-specific first:

1. **An explicit per-provider override**, if this site has customized that provider's tab.
2. **The site's own general template**, if it was ever customized away from BurrowGate's original generic default (see below) - this predates per-provider templates and still applies to any provider that doesn't have its own explicit override.
3. **The provider's own default template**, or BurrowGate's generic default for a provider that doesn't define one of its own.

A brand-new site that has never touched either editing surface always gets provider-tailored defaults automatically, with no admin action needed.

## Placeholders

Placeholder values are HTML escaped before insertion.

```text
{{title}}            Challenge provider title
{{description}}      Challenge provider description
{{siteName}}         Configured site name
{{host}}             Public request host
{{homeUrl}}          Root URL of the protected site
{{provider}}         Active challenge provider name (e.g. pow-sha256)
{{challengeScript}}  Required. BurrowGate injects the bootstrap + client script here.
```

`{{challengeScript}}` is the only required placeholder. BurrowGate replaces it with the challenge bootstrap and the provider's client module (this fragment is generated by BurrowGate and is not escaped). A template that omits it is rejected on save, because the page could never verify.

Some providers expose extra placeholders beyond this generic set, listed in the editor alongside the ones above when that provider's tab is selected - for example Snake's `{{applesRequired}}`/`{{gridSize}}` or Trace's `{{shape}}`. These only cover values fixed when the challenge was created; a value that changes live while the visitor is playing (apples eaten so far, wall touches so far) can't be a placeholder at all, since the page is rendered once, before any of that happens - those stay DOM hooks the client script updates in place, covered next.

## Text

Every string a visitor actually reads during a challenge - status messages, hints, button labels, the redirect countdown - is its own editable text field, listed under **Text** below the placeholder list for the active provider's tab. This is a separate mechanism from placeholders: placeholders are substituted into the page's HTML once, before it's sent; text fields travel to the browser as part of the challenge bootstrap JSON and are read by the client script at runtime (`window.__BURROWGATE_CHALLENGE__.text.<key>`), which is what lets the same string be reused live (in a redirect countdown, for example) without re-rendering the page. Overriding one field only touches that field - every other text field, for every other provider, is unaffected, the same merge behavior templates already have.

A handful of base keys (`verifying`, `redirectingIn`, `redirecting`, `verificationFailed`) are shared by every provider's client script and shown on every tab; each provider then adds its own keys on top - Snake's `goal`/`wallHit`/`selfHit`/`start`, Slider's `hint`/`retry`, Password's `inputPlaceholder`/`submitLabel`, and so on. A few keys carry a `{{name}}` marker for a runtime value the client substitutes in - `redirectingIn` takes `{{seconds}}`, Snake's `goal` takes `{{applesRequired}}`, Trace's `metrics` takes `{{hitCount}}`/`{{maxExcursion}}`. There's no plural-rule engine behind this: a language whose apple count needs different grammar for one vs. many has to be phrased in a way that reads correctly either way, the same limitation English text written in a template would have.

For `snake`, `slider`, `trace`, and `password`, the generic failure text (`snakeChallengeFailed`, `sliderChallengeFailed`, `traceChallengeFailed`, `incorrectPassword`) is also editable here - `verify()` only ever returns that stable key internally, and BurrowGate resolves it to display text (your override, or the provider's own default) right before the response reaches the browser, so translating it doesn't touch the anti-bot logic that decides pass/fail. The other providers' `verify()` failure reasons (a missing token, an unreachable vendor service, and similar) are operational diagnostics rather than something a routine visitor sees, and stay fixed English for now.

## Element contract

Every provider still only requires `id="status"` to exist for status text - present in every default template, and about the only thing every client script has in common. Beyond that, each provider defines its own set of `data-bg-<provider>="..."` hooks: **if a hook is found in the page, the client script wires its behavior onto that exact element - whatever it is, wherever it is, however it's styled - instead of creating a default one.** Anything not found falls back to the same programmatically-created default as before. A template with no hooks at all (every pre-existing custom template included) behaves exactly as it always has - this is what makes the whole scheme backward compatible.

This is also how a control can be remapped or dropped: give an element `data-bg-snake-move="left"` and clicking _that_ element - a styled button, an icon, anything - now steers the snake left, in whatever position your own template puts it. Omit it and there's simply no click control for that direction (Snake's arrow keys still work regardless, as a fallback that doesn't depend on any hook).

## Visual customization (Slider, Snake, Trace)

The piece/target/track colors these three providers draw onto their canvas - and Slider's piece shape (circle or square) - aren't part of the HTML template at all, since a template can't reach into canvas drawing calls. They're per-step config instead, set from the challenge-step editor (Sites -> challenge policy -> that step) alongside settings like Slider's track width or Snake's grid size: color fields as `<input type="color">` pickers, Slider's shape as a dropdown. Two steps using the same provider on the same site can carry different colors, exactly like they can carry different track widths. The values ride in `publicData` and are read directly by the client script (`challenge.publicData.pieceColor`, etc.) - Snake's `backgroundColor`/`appleColor`/`snakeColor`/`snakeHeadColor`, Slider's `pieceColor`/`targetColor`/`trackColor`/`backgroundColor`/`pieceShape`, Trace's `trackColor`/`targetColor`/`trailColor`/`ballColor`/`backgroundColor`.

## Mobile sizing (Trace)

Trace is the one provider where a screen-size mistake was actually shipped and worth calling out: its canvas used to be a fixed 700x450 regardless of viewport, squeezed further by the shared template's `width:min(560px,100%)` `<main>`, which amplifies a touchscreen's physical imprecision far more than a mouse's - a phone's ~5px of finger jitter became ~10 logical px against a track that only had 4px of slack. Trace's canvas is now 460x300 (fits the default template's own content width with no CSS downscaling on desktop at all) and its minimum track width leaves 14px of slack instead of 4 - both tuned for touch, not just "technically positive." An owner-supplied `[data-bg-trace="canvas"]` in a custom template can still pick its own on-screen size (via CSS); the underlying logical canvas and slack stay server-authoritative either way, since `verify()` always replays against `trace-engine.ts`'s own constants regardless of how the page presents it.

## Security

Challenge pages are served with the standard BurrowGate control-plane Content Security Policy, which permits same-origin scripts and workers (the proof-of-work runs in a Web Worker) and the same-origin verification fetch. A provider that needs to load an external widget script or iframe can widen this for its own verification flow only: `hcaptcha` allows `https://*.hcaptcha.com` for scripts, frames, styles, images, and fetches; `turnstile` allows `https://challenges.cloudflare.com` for scripts, frames, and fetches; and `recaptcha-v2`/`recaptcha-v3` allow `https://www.google.com` and `https://www.gstatic.com` for scripts, styles, and fetches, plus `https://www.google.com` for a frame - v3 loads one for its verification even though it has no visible widget. The policy is only widened while that provider's step is active - a `pow-sha256`, `snake`, `slider`, `trace`, or `password` step, or any other provider without extra requirements, still gets the strict same-origin policy. Placeholder values are escaped, and the injected script is inserted after all placeholder substitution so template values can never smuggle markup into the script region.

### Editing the policy per site

Below the Text section in each provider's tab, a **Content Security Policy** section lists the same five directives (`scriptSrc`, `styleSrc`, `imgSrc`, `connectSrc`, `frameSrc`) as space-separated fields, each showing what that provider already allows by default ("Already allowed: ..."). Anything entered here is added on top of that baseline, not a replacement for it - there's no way to narrow a provider's own built-in sources, only widen further. This is what makes a custom-themed template's `background-image: url(...)` actually load if it points at a third-party host: same-origin paths and `data:` URIs already pass the default policy with no configuration, but a truly external CDN needs its host added to `imgSrc` here first, or the browser blocks it silently.

Each source must be a real CSP source expression - a keyword (`'self'`, `'none'`), `data:`/`blob:`, a bare scheme, or `scheme://host` (optionally `scheme://*.host` for a wildcard subdomain). A bare `*`, or anything containing `;`/`,`/whitespace inside one token, is rejected on save, since these values are joined directly into the `Content-Security-Policy` response header.

Each template - the legacy site-wide one and every per-provider override - accepts a complete HTML document up to 131072 characters.
