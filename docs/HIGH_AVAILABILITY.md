# High Availability (Experimental)

**This feature is experimental.** It's had extensive automated test coverage and multiple rounds of review, but has not yet seen wide real-world production use across many different environments and failure scenarios. Test thoroughly against your own setup before relying on it in production, and keep backups regardless.

BurrowGate can run as multiple instances behind a load balancer, with configuration, sessions, certificates, and bans kept in sync across them over an encrypted, certificate-pinned link. Each instance still keeps its own local database and serves proxy traffic from it directly - HA here means the databases converge within about a second of each other, not that instances share one database over the network. That split matters: every proxied request resolves its site, route policy, and network rules from the local database with no network hop in the hot path, and the whole cluster keeps routing traffic even if the replication link is down.

## How it works

One instance is the **primary**; every other instance is a **replica**. This is explicit, persisted configuration (set via `BG_HA_ROLE`, or through the Cluster tab's setup/promote flows - see [Setting it up](#setting-it-up)) - a node's role changes only through a manual Promote, an automatic majority-quorum election, automatic former-primary recovery (a stale primary demoting itself once a majority confirms the real one), or a manual database edit, never silently (see [Failover](#failover)). Promotion and election both carry a cluster epoch that lets nodes detect and refuse a stale primary reconnecting after being demoted, but that's split-brain _detection_, not the physical write fencing that would be needed to fully prevent it (see [Failover](#failover)).

The primary maintains a durable, strictly-ordered **changelog** plus a separate high-watermark row that is never pruned, and runs its own dedicated `Bun.serve()` listener on `BG_HA_PORT` (separate from the public HTTP/HTTPS listeners) that:

"Strictly-ordered" is enforced, not assumed: on PostgreSQL and MySQL, where a row's sequence number is otherwise allocated at INSERT time rather than commit time (so a slower transaction could in principle commit a lower sequence number after a faster one already broadcast a higher one), every write that appends to the changelog first takes a row lock held until that write commits or rolls back - a second write's changelog insert literally cannot begin until the first lock-holder is done. This makes allocation order and commit order the same thing by construction. SQLite's single-writer semantics make this a non-issue there, so the lock is skipped.

- pushes new changelog rows to every connected replica over a websocket the instant they're written, and
- serves `GET /_ha/changelog?since=<seq>` so a replica that just connected (or reconnected after a gap) can pull everything it missed.

A replica connects out to the primary's `BG_HA_PORT` over TLS (see [Transport security](#transport-security)). If it has its own `BG_MASTER_KEY`/`BG_MASTER_KEY_FILE` configured, it verifies that key matches the primary's via an encrypted handshake before trusting anything (a mismatched key would otherwise silently corrupt its view of any replicated encrypted field - TLS private keys, DNS provider credentials); a node with no key of its own instead requests the primary's key over this same authenticated connection and installs it locally (see [Setting it up](#setting-it-up)). Either way, it then catches up and applies live pushes as they arrive.

A brand-new replica (or one that fell behind further than `BG_HA_CHANGELOG_RETENTION_DAYS`, so the incremental changelog can no longer fill the gap) first pulls a full point-in-time snapshot of every replicated entity from the primary rather than trying to replay history that may no longer exist. Snapshot rows are streamed in bounded pages from a repeatable-read database view, so PostgreSQL/MySQL writes do not wait behind a long snapshot and neither endpoint needs the complete dataset in memory. The replica stages the stream locally and only swaps its replicated tables after the complete response arrives; an interrupted transfer leaves its previous state intact. Applying a complete snapshot _reconciles_ rather than upserts - anything present locally but absent from the snapshot is removed too - and every in-memory cache and the load balancer's origin map are refreshed once it lands.

A replica also self-heals from a row that simply won't apply: a transient failure (a momentary DB lock, a connection dropped mid-write) resolves on the very next reconnect-and-retry, but the same row failing the identical way three times in a row is treated as non-transient, and the replica forces a fresh full snapshot on its next connection instead of retrying it forever.

Not everything replicates the same way, because not everything is written by the same node:

- **Single-writer data** (config and account-management changes an admin edits) is written only on the primary. If a replica receives one of these admin API writes, it transparently forwards the whole HTTP request to the primary and relays the response back - the browser never needs to know which node handled it.
- **Multi-writer data** (sessions, auto-bans, and identity changes intrinsic to a login ceremony such as SSO provisioning or TOTP enrollment) can legitimately originate on _any_ node. A replica writes these locally immediately and relays the event up to the primary, which assigns it a real changelog position and fans it back out to every connected node - including the one that originated it. That node already has this exact state from its own direct write, so it skips re-applying the payload from its own echoed-back event (while still advancing the watermark bookkeeping) rather than risk a delayed, stale overwrite of any newer local write made in the meantime. Identity updates are relayed as field patches rather than stale whole-row replacements. Each installation has a generated, immutable node UUID (separate from `BG_HA_NODE_NAME`), sends one queued event at a time in increasing outbox-id order, and advances a replicated per-node relay watermark atomically with the event. That bounded watermark survives promotion and makes a retry after a lost acknowledgement a no-op without an ever-growing receipt table. IDs may skip after a rolled-back local transaction; only monotonic order matters.

## What replicates

**Single-writer** (primary-only; a replica always forwards these admin writes to the primary):

| --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Streams, stream-level country/ASN rules, stream-level IP rule deletes | A replicated stream change binds/rebinds or tears down that node's own live listener for it, same as a direct edit does. Stream-level IP rule _inserts_ are the one exception - see the multi-writer table below                                                                                                          |
| DNS providers                                                         | Credentials are decrypted with `BG_MASTER_KEY` on whichever node applies them                                                                                                                                                                                                                                             |
| Certificates, TLS settings, ACME HTTP-01 challenges                   | A replicated certificate/TLS-setting change also triggers a live reload of that node's own HTTPS listener                                                                                                                                                                                                                 |
| ACME account (per directory URL)                                      | So a promoted replica renews under the same Let's Encrypt account the primary registered, instead of silently creating a new one on its first renewal                                                                                                                                                                     |
| Site access settings, admin SSO settings, site SSO settings           |                                                                                                                                                                                                                                                                                                                           |
| Admin/access-user management, password/token/TOTP resets              | Forwarded to prevent stale multi-node whole-record updates                                                                                                                                                                                                                                                                |
| Firewall sync provider config, IP whitelist                           | Unlike ACME renewal, the scheduled sync itself runs on every node, including replicas - a sync target is frequently node-local (the nftables adapter can only ever manage the machine it runs on) or per-node (a separate cloud firewall per VPS), not one shared resource every node should agree on a single pusher for |
| Scheduled site/stream changes (pending changes)                       | Only the primary's own scheduler (`BG_PENDING_CHANGES_POLL_INTERVAL_SECONDS`) applies these when they come due, so a promoted replica keeps whatever was still scheduled rather than losing it                                                                                                                            |

**Multi-writer** (any node writes locally and relays; no forwarding involved):

| Data                                                                              | Notes                                                                                                                                                                                                                                                                                                        |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Admin and access sessions                                                         | This is what makes the dashboard work without a sticky load balancer - see below for how a login on a replica is made visible elsewhere before its cookie is even returned                                                                                                                                   |
| Site-level IP/country/ASN bans                                                    | Covers automatic bans from protection rules and bandwidth limits, not just admin-added rules                                                                                                                                                                                                                 |
| Stream-level IP rule inserts                                                      | Same reasoning as site-level bans above, scoped to IP rules only - a bandwidth-limit or protection-rule auto-ban is triggered by live traffic on whichever node is terminating that stream connection, with no admin request to forward. Stream-level country/ASN rules and all deletes remain single-writer |
| Admin users, access users                                                         | Login-local enrollment/linking and deterministic SSO auto-provisioning; admin edits are forwarded                                                                                                                                                                                                            |
| Admin recovery codes, admin/access WebAuthn credentials                           | Enrollment/replacement relays normally; _consuming_ a recovery code is the one exception - see below                                                                                                                                                                                                         |
| Site ↔ access-user assignments                                                    |                                                                                                                                                                                                                                                                                                              |
| Admin RBAC assignments (which sites/streams a non-administrator admin can manage) |                                                                                                                                                                                                                                                                                                              |

**Certificate renewal** (`BG_ACME_CHECK_INTERVAL_SECONDS`-driven auto-renewal) only runs on the primary - a replica skips it outright rather than racing Let's Encrypt independently for the same certificate.

**Recovery-code consumption is the one deliberate exception to multi-writer availability.** Granting a security-sensitive one-time credential twice - two replicas both accepting the same code locally before either sees the other's eventually-consistent relay - is worse than that one rare login path being briefly unavailable, so a replica calls the primary synchronously to consume a code instead of applying it locally and relaying. If the primary can't be reached, the login attempt fails rather than falling back to a locally-racy check.

**A login on a replica is durably visible before its cookie is even returned.** A session created on a replica is written locally immediately (so the response isn't held up by network latency), but the HTTP response itself waits for the primary to have acknowledged the relay before the cookie is handed back - closing the otherwise-visible interval where a freshly-logged-in user's very next request, if load-balanced to a different node, would bounce them back to login. If the primary doesn't acknowledge within the publication deadline (10 seconds - a genuinely unreachable or badly degraded primary, not normal replication lag, which round-trips in well under a second), the login attempt fails outright rather than silently handing back a cookie that might not work anywhere else yet.

This closes the write side of the race; a second, narrower gap remains on the read side even after that acknowledgment - the primary has the session, but its own fan-out to every _other_ replica is still on the usual ~500ms broadcast tick. A replica whose local session lookup misses therefore asks the primary directly (`POST /_burrowgate/api/admin/ha/resolve-admin-session`, gated by the same shared-token bearer auth as the certificate-bootstrap and recovery-code routes - internal HA-to-admin-API traffic, not a browser-facing endpoint) before concluding the session doesn't exist. A session resolved this way isn't inserted locally (that would create a redundant relay of an already-primary-owned row); the primary's own touch on that route keeps its `last_seen_at` current instead. If the primary can't be reached for this lookup either, authentication falls back to a plain local miss rather than blocking the request - unlike the write side above, this fallback has a real substitute (the eventually-consistent fan-out will catch up), so there's no publication-style hard failure here.

## What doesn't replicate, and why

- **Runtime/operational data** - request events, bandwidth counters, health-check status, system metrics, notification/audit logs. This is genuinely per-node telemetry; replicating it would just mean answering "how much traffic has this cluster seen" with a merge query instead of a single number, for no correctness benefit.
- **High-frequency touch fields** - `last_seen_at`/`request_count` on sessions, `sign_count`/`last_used_at` on WebAuthn credentials. These fire on every authenticated request; replicating them would be a lot of write traffic for pure telemetry. The one field this trades away is a narrow one: an unreplicated WebAuthn `sign_count` on a node other than the one that just handled a login is a slightly weaker clone-detection signal on that specific node, not a new class of vulnerability.
- **Routine TTL cleanup** (expired sessions, expired ACME challenges) - every node reaches the same expiry judgment independently once the row's `expires_at`/`revoked_at` has already replicated, so replicating the cleanup deletes themselves would be redundant.
- **Lazily-created default rows** (e.g. a site's TLS settings before anyone has touched them) are deterministic and harmless to create independently on each node - only an explicit save replicates.

## Setting it up

The fastest way to form a cluster is through the **Cluster** tab in the dashboard - no `BG_MASTER_KEY` pre-provisioning required (see below). HA is always on, so a fresh node is already a primary of a cluster of one the first time this tab loads; there's no separate "enable HA" step:

1. On a fresh node, open the Cluster tab's **"This node's identity"** card and give it a name and its own reachable **HTTPS** admin URL, then **Save**. This applies immediately, no restart - it's a plain identity edit, not a role change.
2. Click **Generate join code** (shown once this node is a primary with its identity set) to get a copy-pasteable code bundling everything a second node needs to enroll: the primary's mesh and admin URLs, its public mesh certificate, and a short-lived (15 minute), single-use enrollment credential - never a standing secret itself (see below).
3. On a second, fresh node, open its own Cluster tab's **"Join an existing cluster"** card, paste the code in, and give that node's own reachable admin URL, then **Join cluster**. This makes a real network call back to the primary (redeeming the enrollment credential for a bearer credential of this node's own over `/_ha/enroll`, gated on the enrollment credential rather than anything it exists to hand out) - so unlike the rest of this step, it genuinely requires the primary to be reachable at join time.

**The join code carries a one-time credential, and enrollment mints a credential unique to the joining node - never a secret shared across the cluster.** Earlier versions of this join code embedded a single bearer credential every node used for every mesh request, directly in the copy-pasted blob - so anyone who ever saw one (a chat log, a screenshot, shell history) had indefinite, unrevocable mesh access, and no node's access could be revoked without breaking every other node too (they all shared the exact same secret). Generating a fresh join code now mints a new enrollment code instead (hashed at rest, the same way recovery codes and access-list tokens are), redeemable exactly once within 15 minutes for a fresh, random per-node credential over a dedicated mesh endpoint - each enrolling node gets its own, distinct from the primary's and from every other member's. Requesting a join code any number of times is fine - each call mints an independent enrollment credential; nothing revokes an earlier, still-valid one just because a newer one was requested. A member's own credential is what **Forget** actually revokes - see [Version-safe upgrades](#version-safe-upgrades). Redeeming one against an election-capable primary also requires that primary to currently hold majority connectivity to its existing membership - see [Automatic failover](#automatic-failover) - so a primary isolated by a partition cannot grow the cluster with reachable-but-brand-new nodes to manufacture its own majority while the genuinely majority-holding side elects a real replacement; the still-valid code simply works once redeemed again after connectivity is restored.

Step 3 (and **Promote**/**Leave cluster**, below) restarts the node it's run on to apply the change (the role/URLs live in a database table from that point on, not env vars) - the dashboard shows a "restarting" state and reloads automatically once the node is back. This only works if the process comes back up on its own after exiting (Docker's `restart: unless-stopped`, or an equivalent systemd/supervisor policy) - if it doesn't, the node stays down until started manually, same as it would for any other crash.

**Joining replaces this node's replicated data with a full copy of the cluster's.** Whatever this node bootstrapped from - a genuinely fresh database, or its own accumulated sites/config while it was still a standalone primary - is discarded once it connects to the new primary in favor of an exact copy of what the primary has (see [How it works](#how-it-works) on `reconcileToSnapshot`). This also applies when re-joining a _different_ cluster after **Leave cluster** (below): the node's bootstrap state is reset on every join, so it always pulls a correctly-scoped fresh snapshot rather than resuming incremental catch-up against an unrelated primary's changelog.

A replica can leave its cluster from its own Cluster tab by clicking **Leave cluster** - it becomes a standalone primary of a new cluster of one again, with a freshly generated shared token (the old cluster's token is no longer usable to rejoin it) and its previous name/admin URL kept. Its data is left untouched (only joining wipes and replaces data, not leaving). Like joining or promoting, this restarts the node to apply. Leaving doesn't affect the rest of the cluster - the remaining nodes just no longer hear from it.

**`BG_MASTER_KEY` no longer has to be pre-provisioned to join.** A node with no master key of its own (neither `BG_MASTER_KEY` nor `BG_MASTER_KEY_FILE` set, and none previously auto-provisioned) requests it from the primary automatically right after connecting, over the same TLS-and-credential-authenticated mesh channel used for everything else, and stores it locally (`<data directory>/master.key`). This never travels through the join code itself - the join code's enrollment credential only ever yields this node's own per-node mesh credential (see above), and the master key request is a second, separate step gated on already holding that credential to open the mesh WebSocket in the first place. An operator who sets `BG_MASTER_KEY`/`BG_MASTER_KEY_FILE` explicitly on a node is never affected by this - that key is always used as-is, and a genuine mismatch against the primary still surfaces loudly as `key_mismatch` rather than being silently "fixed" by auto-fetching a replacement.

HA is always on - there's no env var to enable or disable it, and a node that hasn't joined a cluster is simply the primary of a cluster of one (it seeds itself a random bootstrap credential and starts listening on `BG_HA_PORT` the same as any other primary would). The env vars below still exist and are still useful for scripted/IaC deployments of a **primary**, but they only ever _seed_ a node's very first boot (mirroring how the bootstrap admin user works) - once a node has booted once, its role/URLs/credential live in a database table, and env vars are never consulted again. A stale `BG_HA_ROLE` left in a `.env` file after a node was promoted or joined through the UI has no effect.

**A replica's first-ever boot must go through the join-code/enrollment handshake - there is no purely env-var-driven way to bootstrap one.** Earlier versions of this feature let a scripted replica boot directly with `BG_HA_ROLE=replica` plus a `BG_HA_SHARED_TOKEN` value copied from the primary, skipping the UI entirely. That relied on every node authenticating with the literal same bearer secret, which per-node credentials (above) deliberately replace: a replica's mesh credential now has to be minted by the primary for that specific node's UUID through `/_ha/enroll`, so there's no value an operator could pre-know and hand a not-yet-provisioned node. A script can still automate this without touching the dashboard by driving the same two calls the UI does against the primary's admin API - generate a join code (`POST /_burrowgate/api/admin/ha/join-code`) and redeem it as the new node (`POST /_burrowgate/api/admin/ha/join`, which performs the `/_ha/enroll` round trip itself) - but `BG_HA_SHARED_TOKEN`/`BG_HA_ROLE=replica` alone no longer works for a node's first boot.

| ---------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `BG_HA_ROLE`                             | `primary`                | `primary` or `replica`, only consulted on a node's first-ever boot                                                                                                                                                                                           |

| `BG_HA_SHARED_TOKEN`                     | auto-generated (primary) | Primary only: this node's own bootstrap mesh credential, used as its "cluster of one" identity until other nodes join. Setting it on a replica does not work - see the note above; every node's actual mesh credential is minted per-node through enrollment |
| `BG_HA_RECONNECT_MIN_DELAY_MS`           | `1000`                   | Replica's initial reconnect delay after a dropped connection                                                                                                                                                                                                 |

| `BG_HA_CA_FILE`                          | -                        | Replica only: manually pin this certificate instead of auto-fetching and pinning the primary's                                                                                                                                                               |
| `BG_HA_NODE_NAME`                        | hostname                 | This node's display name in the Cluster dashboard tab and node-down notifications                                                                                                                                                                            |

`BG_HA_NODE_NAME` does not participate in replication identity and does not need to be unique. BurrowGate stores a generated node UUID in the node's local database; a fresh database receives a fresh UUID so recycled relay sequence numbers cannot collide with an earlier installation.

**`BG_MASTER_KEY` must be identical on every node that has one configured**, or the cluster silently breaks rather than erroring loudly at some layers - this applies to any node whose `BG_MASTER_KEY`/`BG_MASTER_KEY_FILE` is set explicitly; a node joining through the UI (or the equivalent scripted `/_ha/enroll` round trip) with neither set gets its key auto-provisioned instead, so it's a non-issue there (see the note above). It decrypts TLS private keys and DNS provider credentials stored in replicated rows. A mismatch is caught explicitly at connect time (the replica marks itself unhealthy and logs an error instead of applying anything), but it's still worth getting right from the start. There is no equivalent standing secret for the mesh credential itself anymore - each node's is unique and minted through enrollment, not something to copy between nodes.

Each node needs its own `DATABASE_URL` (or its own database if you're pointing at Postgres/MySQL instead of SQLite) - HA here is about syncing separate databases, not sharing one.

A primary needs no HA env vars at all - a fresh node defaults to `primary` and generates its own bootstrap credential on first boot. A replica has no equivalent purely-env-var first boot (see the note above) - it needs `BG_HA_ROLE=replica`, `BG_HA_PRIMARY_URL`, and `BG_HA_PRIMARY_ADMIN_URL` set to know where to enroll, but the credential itself always comes from redeeming a join code against the primary, whether through the dashboard or a script driving the same admin API calls.

`BG_HA_PORT` (7443 by default) needs to be reachable from every replica to the primary, but should not be exposed publicly - it's the whole replication trust boundary, gated by both TLS and each node's own mesh credential. Because HA is always on, this port is always listening, even on a node that will never join a cluster - firewall it accordingly.

## Transport security

`BG_HA_PORT` runs TLS, not plain HTTP/WS - some replicated data (admin/access password hashes, in particular) shouldn't cross the network in the clear. This works with no manual certificate handling in the common case:

Every admin/topology URL used by HA must also be absolute `https://` without embedded URL credentials. This is enforced when identity is saved, when a node joins or announces itself, on election/redirect/discovery messages, and again from persisted configuration at startup. A node upgraded with an old `http://` HA URL refuses to start until that address is corrected; `BG_HA_CA_FILE` secures the dedicated mesh certificate but does not make a plaintext admin API safe.

- **Primary**: generates a self-signed certificate on first start (`data/tls/ha-cert.pem`/`ha-key.pem`, 10-year validity) unless `BG_HA_TLS_CERT_FILE`/`BG_HA_TLS_KEY_FILE` point at one you'd rather provide - e.g. one issued by an internal CA. This certificate is cached in memory for the life of the process, not re-read from disk on every use: `Bun.serve()`'s own TLS context is fixed the moment the mesh listener starts and never hot-reloads if the underlying files change afterward, so every other consumer in this same process (the dashboard's own bootstrap TLS fallback, and join-code generation) has to keep agreeing with whatever that listener actually presents for as long as the process runs, not whatever the files happen to say right now. Regenerating the certificate (deleting `ha-cert.pem`/`ha-key.pem` and letting it be recreated) always requires restarting the process that owns it to take effect - on the primary specifically, restarting anywhere _other_ than the primary cannot fix a certificate mismatch, since the primary is the only node whose in-memory copy is what a joining replica's handshake actually has to match.

**The generated certificate's SAN covers this node's own configured admin URL, not just `localhost`/`127.0.0.1`.** This matters more than it would for an ordinary TLS client: confirmed directly (a real server/client pair, an address deliberately absent from the certificate's SAN) that Bun's _native `WebSocket`_ TLS implementation does not honor a `checkServerIdentity` override the way `fetch()` correctly does - a replica's WSS connection to a primary reachable only by its real LAN IP or hostname could never succeed against a certificate whose SAN only ever listed the loopback addresses, no matter what trust options the connecting code supplied. The only way to actually close that gap is generating the certificate so its own SAN already covers the address a replica will really connect to, so ordinary hostname verification passes on its own - this is why `haTlsCertificate()` reads `config.ha.selfAdminUrl` (an IP literal becomes an `IP:` SAN entry, anything else a `DNS:` entry) when it generates a certificate, alongside the fixed loopback entries. A certificate whose SAN doesn't cover this node's current `selfAdminUrl` - generated before this fix existed, generated before `selfAdminUrl` was ever configured, or simply left over on disk from an earlier stint as primary before a later promotion - is detected and regenerated automatically the next time this function runs (no manual deletion needed): `resolveHaTlsCertificate()` checks the existing file's actual SAN against the currently-configured address before reusing it, not just whether the files exist. This was found in production: a node promoted to primary reused a stale cert left over from before it had ever needed one, reproducing the exact hostname-verification failure above via a different path than the one the SAN fix itself closed.

- **Replica**: receives the public certificate in the authenticated join code (whether obtained through the UI or the equivalent scripted `/_ha/enroll` round trip - see the note above), uses it to verify the enrollment request itself, and persists it to `data/tls/ha-primary-ca.pem` before restarting. Every later connection is verified against that exact pinned copy. `BG_HA_CA_FILE` may instead pin a different certificate manually.

**A pinned certificate that goes stale without any role change ever telling this replica to re-pin self-heals on its own.** The primary can regenerate its own certificate independently of any role change (the self-healing SAN check above is exactly this case), which leaves an already-pinned replica's copy simply wrong - not a hostname-mismatch problem this time, a completely different certificate. Rather than retry forever against a CA that no longer matches anything the primary serves, a replica whose connection closes with a 1015 ("TLS handshake failed" - Bun's code for exactly this failure) while it has a pinned certificate clears that pin and lets the next reconnect attempt fetch a fresh one through the same bearer-token-authenticated bootstrap path used to establish trust the first time (see `resolveCaCertificate`'s own comment on why that path doesn't need CA trust to be safe). This automates what was previously a manual "delete the pinned file and restart" recovery step.

This deliberately isn't the same as accepting any self-signed certificate: an unverified handshake stops passive eavesdropping but not an active interception, since an attacker could present their own certificate just as easily. Pinning the exact certificate closes that gap - only the primary can ever complete a handshake using the certificate the replica trusted.

Trust comes from the authenticated admin page (or admin API caller) that produced the join code, and the certificate pins the very first enrollment connection.

To force a replica to re-pin (e.g. after deliberately rotating the primary's certificate by deleting its `ha-cert.pem`/`ha-key.pem`), delete that replica's `data/tls/ha-primary-ca.pem` and restart it - it re-fetches and re-pins the primary's current certificate automatically (see below for how that fetch authenticates without a CA-trusted admin URL).

**This pinning also covers each node's admin URL, not just the mesh port.** A node's admin URL - the address other cluster members use for admin-to-admin HTTP calls (a replica forwarding an admin write to the primary, resolving a session that lives on the primary, or re-fetching the primary's certificate after a promotion) - is frequently a bare IP or an internal hostname with no publicly-trusted certificate available. Whenever HA is enabled, the dashboard's own bootstrap TLS fallback (served whenever no site's SNI hostname matches - exactly the case for an admin URL that's a bare IP) reuses this node's HA certificate instead of generating a separate one, and every admin-to-admin HTTP call verifies the far end against the same pinned certificate the mesh connection already trusts, rather than the system CA store. A real, CA-trusted certificate on the admin URL is still honored normally - this only changes what happens when it isn't one.

**Re-fetching a certificate to pin in the first place - the one operation above that has nothing to verify against yet - authenticates via the shared token, not the system CA store either.** Whenever a replica has no pinned certificate at all (a fresh `data/tls/ha-primary-ca.pem` deletion, the raw `BG_HA_ROLE=replica` bootstrap path with no join code, or re-establishing trust in a newly promoted primary), it fetches the primary's certificate over the admin URL and pins whatever comes back. Requiring that admin URL to already be CA-trusted would make this fetch permanently fail against the self-signed certificate every private/internal deployment actually has - which would leave the documented re-pin recovery above non-functional for the common case. Instead, this request's own `Authorization: Bearer` header - the node's long-lived shared token, already proving it is an established cluster member - is what authenticates it; the transport-level certificate is not required to be CA-trusted. This is the same trust model already used for join-code enrollment (a secret proves identity, not a CA chain), extended to cover re-pinning too. The narrow accepted risk: an active attacker who could intercept this one specific request could feed it a fake certificate to pin - the same class of risk already accepted for the initial join-code handshake, not a new category.

**Provisioning a new node from a copied database**: don't. Each node generates its own immutable identity UUID on first migration (`ha_node_identity`), used to attribute relayed multi-writer events (sessions, bans, identity changes) back to the node that originated them. Copying a node's data directory to bootstrap a second instance copies that UUID too, and the primary will refuse the second connection outright (`a node with this identity is already connected`, logged at `error`) rather than let two nodes share one relay watermark - a legitimate event from one clone could otherwise be silently discarded as an already-seen duplicate of the other's. Provision a new replica the normal way instead: start it with an empty data directory and join it to the cluster (via the Cluster tab's join code, or `BG_HA_ROLE=replica` pointed at the primary) - it gets its own UUID and a full bootstrap snapshot automatically (see [How it works](#how-it-works)). If you do need to reuse a copied directory (e.g. restoring from a backup onto new hardware), delete the single row in `ha_node_identity` first so a fresh UUID is generated on next start. A node stuck in this rejected state backs off exponentially between attempts rather than retrying at the minimum delay forever, so it can't win a reconnection race against the legitimate node after the primary restarts.

## Load balancer requirements

Point your load balancer's health check at `GET /_burrowgate/health`. A replica that hasn't completed its first bootstrap snapshot yet reports `503`/`"starting"` - it may have an empty or partial database, so it should stay out of rotation until then. A replica also reports `503` when its application version differs from the primary, its master key cannot be verified, its connection is rejected, or it detects a stale primary epoch. These standing failure states never receive the ordinary disconnect grace period. Every replica restart begins unready until that process has freshly authenticated to and caught up with the primary; an old on-disk bootstrap does not grant a new grace window by itself. Once it has verified a connection, it remains `200`/`"ok"` through a short ordinary disconnect so a momentary network flap does not churn the load-balancer pool. That grace period is `BG_HA_DISCONNECTED_READY_GRACE_SECONDS` (60 seconds by default); after it expires the replica reports `503` until it catches up again. While connected, primary heartbeats advertise the current changelog watermark; failure to receive and reach one within `BG_HA_MAX_SYNC_STALENESS_SECONDS` (30 seconds by default) also reports `503`, covering half-open sockets and an apply queue that has fallen behind without disconnecting. A primary is ready once its listener is up only while it has no promotion fence, stale-authority fence, or [quorum-loss fence](#automatic-failover) - the last of these clears itself automatically once majority connectivity returns, unlike the other two. A replica that's genuinely stuck - the same changelog row has failed to apply three times in a row, which forces a full re-bootstrap on its next connection instead of retrying forever - drops out of `200`/`"ok"` immediately.

**A replicated row applying to the database is not the same as this node's live runtime state actually reflecting it.** Reloading the TLS listener, refreshing the load balancer's origin map and health checks, and binding/tearing down a stream's port are all separate steps that happen after a row's already-durable database write, and any one of them can fail independently (a filesystem permission problem writing a cert, a port already in use) without the write itself being in doubt at all. A replica whose database is current but whose runtime failed to keep up drops out of `200`/`"ok"` immediately, the same as a stuck apply - silently continuing to serve traffic under a stale TLS cert or a stale origin map would be worse than a brief `503`. Unlike a stuck apply, there's nothing else that would necessarily retry this on its own (nothing more may ever replicate for the affected entity type), so a dedicated timer keeps retrying a full runtime reconcile every heartbeat interval while fenced. If that keeps failing for three consecutive attempts, the process restarts - not a re-bootstrap, since the database itself was never in question, and every one of these subsystems already initializes fresh from the current database at boot anyway.

Proxy and dashboard traffic can be freely round-robined across all nodes - sessions replicate, so a request landing on any node recognizes a login that happened on any other node within about a second.

The one exception is **mid-flight login ceremonies**: WebAuthn registration/verification and SSO callbacks (`/_burrowgate/admin/sso/callback`, `/_burrowgate/access/*/sso/callback`) hold short-lived state (a challenge, a PKCE verifier) in memory on whichever node started the ceremony - not yet replicated. If the load balancer routes the second half of one of these flows to a different node than the first half, that login attempt fails and has to be retried. If your load balancer supports it cheaply, enabling session affinity (sticky-by-cookie) for just the login-related paths avoids this; it isn't required for anything else.

ACME HTTP-01 validation (`/.well-known/acme-challenge/*`) needs no such pinning - challenge tokens replicate, so whichever node the CA's validation request happens to hit can answer it.

## Version-safe upgrades

Every registered node in a cluster must run the exact same BurrowGate application version before the primary accepts configuration changes. As soon as either side of a mesh connection reports a different version, the replica refuses that replication stream and drops out of `/_burrowgate/health`, while the primary returns HTTP `409` with code `cluster_version_mismatch` for mutating admin API calls. Existing proxy traffic, logins, reads, logout, and the HA recovery actions remain available; the fence is specifically there to stop configuration produced by one release from being interpreted by another.

Membership and each node's last reported version are durable and replicate with the rest of the cluster. An outdated replica therefore continues to fence writes while it is offline and after the primary restarts or another compatible node is promoted; disconnecting it is not a way around the safety check. The Cluster tab lists these offline members and their last-seen time. If a machine has intentionally left the cluster or has been permanently decommissioned, stop it and use **Forget** on the primary. A connected node cannot be forgotten, and neither can one that merely _stopped_ being connected too recently - Forget also requires the primary to have seen it disconnected for a while (a fixed floor, or three times this cluster's own configured reconnect ceiling, whichever is longer), so a still-alive node caught in an ordinary reconnect cycle or a brief network blip can't be forgotten by mistake. This tracking is live-only on the current primary process, not durable - a primary restart resets it, which only ever makes Forget momentarily _more_ conservative right after a restart, never less. Forget clears that node's own mesh credential and leaves a replicated revocation tombstone, so a stopped node that still has its old credential cannot silently register itself again after this primary restarts or another replica is promoted - it did not just lose its entry from the member list, its actual credential stopped working. To deliberately return that same node identity, join it again with a newly generated one-time join code; successful enrollment atomically clears its tombstone before reconnecting.

This cooldown is about human error, not split-brain: it doesn't change the pre-existing, separate majority-connectivity check right above it (which does exist for split-brain safety - see its own comment in `forgetNode`). On that note, membership changes themselves (join or forget) are not staged behind any kind of cross-node consensus - the primary's own view of the member count is always read fresh, never cached, everywhere it's used for a safety decision, and the node that performs the change (the primary) always has the immediately-correct count for itself, while any replica that hasn't yet replicated the change can only ever be stale in the direction that makes its own vote/fence threshold _harder_ to satisfy alongside the primary's newly-updated one, never easier - so a lagging membership view cannot itself produce two simultaneous majorities, **as long as both sides stay at or above the automatic-failover floor**.

That qualifier matters: below the floor, quorum-loss self-fencing is skipped entirely (see [Automatic failover](#automatic-failover) - "no election can ever happen anywhere in this cluster, so fencing here would be a pure availability cost"), which is only true once _every_ node agrees the cluster is that small. A membership shrink crossing the floor - most commonly this primary's own Forget - updates this node's local view first; other registered members that haven't replicated it yet remain fully election-eligible under their own still-larger view. Naively trusting the new, smaller count the instant it's observed locally would let this primary stop proving quorum connectivity at all at exactly the moment a stale-viewing peer might still legitimately elect a replacement - a real gap a third-party review found. Closed with a bounded grace window (`MEMBERSHIP_SHRINK_GRACE_MS`, in-memory, comfortably longer than the worst-case time a stale-viewing peer could still be mid-campaign under the old view): for that long after last confirming a higher member count, the primary keeps evaluating the floor and majority against that older, larger count rather than the freshly-observed smaller one - only real, currently-registered members can ever supply a live connection either way, so this only holds the bar at what it used to be, never invents connectivity that isn't there. This in-memory tracking alone would not survive a restart, so a primary that crashed and restarted immediately after its own membership-shrinking Forget would otherwise start the grace window over with no memory of the larger count, right as `prepareForRuntimeAtBoot`'s own boot-time quorum fence made the identical "trust whatever the local count is right now" decision - a second, narrower instance of the same hazard. Closed with a durable counterpart: `forgetNode` records the pre-forget member count (`recent_max_member_count`/`recent_max_member_count_at` on `ha_cluster_config`) in the exact same database transaction as the member removal itself, not a separate follow-up call whose own failure (or a crash between the two) could durably remove the member while never recording what the count used to be. The boot-time fence checks the durable value the same way the running tick checks its in-memory version - if it's still within the grace window and larger than the freshly-loaded local count, the boot decision uses the larger, durable one. This holds for ordinary sequential membership changes; it is not full joint consensus, and isn't meant to replace the majority-connectivity check above.

**Why a time-based grace window is enough here, without full joint consensus** (re-confirmed twice under third-party review, including specifically for a genuinely long-lived - not just brief - partition on the other side): for the grace window's elevated threshold to matter at all, this primary must stay connected to enough real peers to satisfy it; those peers, being connected to their verified primary, cannot simultaneously be voting anywhere else (an existing, unrelated rule). The instant any of them disconnects, this primary's own majority check - still using the elevated, grace-protected threshold - fails immediately through the ordinary always-active connectivity mechanism, not gated on the 120-second timer at all. So the only way the grace window's actual expiry is ever reached is if nothing defected the whole time, in which case there was nothing unsafe happening regardless of when the threshold finally relaxed. This general argument - a lagging side can only ever be stale in the direction that raises its own required majority - holds for a stale VIEW of _pre-existing_ membership, on either the shrink or grow side. It does not, on its own, cover growth from brand-new capacity: an isolated primary could otherwise enroll nodes it can still reach that never existed in anyone else's view at all, inflating its own denominator with capacity the majority-holding side has no way to know about, rather than merely having a stale view of a fixed pool both sides are drawing from. `handleEnrollRequest` (the join-code redemption endpoint) therefore requires the same current-majority-connectivity precondition `forgetNode` already does before it will mint a credential for a new member - exempted below the automatic-failover floor for the same reason Forget's own check is, and refusing (rather than consuming the one-time code) so the joining node can simply retry once this primary has genuinely regained majority.

That precondition at issuance is necessary but not sufficient on its own: a code redeemed while the cluster was still healthy remains a perfectly valid credential and can be used to connect much later - including mid-partition - at which point the enrollment-time check never runs again. The transaction that actually matters for split-brain safety is activation itself: `recordClusterMember`, called from the announce handler once a node authenticates, is what sets `activated_at` and makes a node count toward `haClusterMembers()`/quorum math - and a third-party review correctly pointed out that this step had no majority check of its own, leaving the same brand-new-capacity gap open via any credential issued before an isolation began. The announce handler now applies the identical `majorityConnectivityShortfall` precondition immediately before `recordClusterMember`, but only for a node that is not yet active (`!ws.data.authenticatedActive`, reflecting its durable state as of authentication) - an already-active member's routine reconnect is deliberately never gated here, since blocking that would perversely stop the one thing that could help this primary regain majority in the first place. A refusal at this point closes the socket (matching the existing "activation transaction did not commit" retry pattern) without consuming the credential, so the joining node simply reconnects once majority is genuinely restored.

**Membership activation requires durable confirmation from a majority of the OLD membership, not just proof that they were reachable a moment ago.** An earlier version of this guard (`majorityConnectivityShortfall` alone, then a follow-up fresh liveness-ack round) still only proved a peer _replied to something_ - a bare round-trip with no content. A further third-party review found that insufficient too: two nodes could activate concurrently, each acked by the same reachable peer, moments before that peer (and the rest of the old membership) were partitioned from this primary. Reachability alone says nothing about whether the OTHER side of that partition ever actually received the change - it could go on believing the old, smaller membership and elect a competing primary under it. Two durable, simultaneously-writable primaries, neither of which is merely a stale view of the same fixed node set.

What actually closes this: `haElectionService`'s own campaign logic reads `repository.haClusterMembers()` fresh from each node's _local_ database at campaign time, never a cached or primary-reported count (see [Automatic failover](#automatic-failover)). So if a majority of the old membership has genuinely _applied_ - not just acknowledged reachability for - the changelog row that added a new member, their own future majority arithmetic already reflects the larger membership too. They can no longer independently reach the old, smaller majority even if they wanted to; there is no stale view left to exploit. Proving reachability was never going to be enough - what's needed is proof of durable replication, the same thing `waitForMajorityDurability` already exists to prove for ordinary writes.

`waitForMembershipActivationDurability` reuses that exact mechanism rather than inventing a separate one: `recordClusterMember` still writes and commits the activation first (assigning it a real changelog seq), then this waits - via the same `CursorMessage`-driven `lastAckedSeq` tracking, the same immediate broadcast-kick, the same poll cadence as `waitForMajorityDurability` - for a majority of the _pre-activation_ membership specifically (captured before the write, since the newly-added node's own cursor doesn't count toward confirming its own addition, and `haClusterMembers()` already includes it by the time this runs) to durably confirm they applied at least through that seq. If a majority confirms in time, the activation stands. If not - the pre-activation membership was genuinely unreachable, or became so right after the write - `revertHaClusterMemberActivation` puts the row back to pending (not revoked) in the exact same durable, replicated fashion, so the same credential remains valid and the joining node simply reconnects and retries once this primary genuinely regains durable majority connectivity. Exempt below the automatic-failover floor for the same reason every other check in this section is: a cluster that small cannot form a competing automatic primary regardless.

This is deliberately _not_ full persisted joint consensus with separate propose/commit log phases - it reuses the durability-confirmation machinery this codebase already has rather than building new staged-configuration infrastructure. A primary crash between the write and confirmation just leaves the row durably active on this node (as any crash after any other write would); on restart, this node's own boot-time quorum fence (see the membership-shrink grace window above) and the ordinary always-active `tickPrimaryQuorum` check still require _genuine, current_ connectivity to satisfy majority before this node can write anything - a crash never manufactures majority on its own, restart or not.

Testing this durable-confirmation path against genuinely concurrent activations surfaced an unrelated gap: two writes starting close enough together, from two different connected sockets (two nodes announcing at once, or two replicas relaying events simultaneously), could begin overlapping transactions on this process's single shared SQLite connection - which the driver rejects outright with "cannot start a transaction within a transaction." Already handled gracefully by the ordinary write-failure path (the losing side is refused, cleanly and retryably, never left half-active), so this was a reliability gap under real concurrent load rather than a correctness one - but the primary side of the mesh listener had no cross-socket write serialization at all, unlike the replica side's own single-connection message queue. Closed the same way: `announce` and `relay` - the only two message types that actually perform a serialized DB write - are chained through one `primaryMessageQueue`, so two writes can never actually overlap regardless of how close together they arrive.

Everything else (`cursor`, and the various promotion acks) deliberately bypasses that queue and dispatches immediately. This split is load-bearing, not an optimization: queuing every message behind one chain deadlocks the moment an activation is mid-flight, because `waitForMembershipActivationDurability` (and, for the identical reason, `waitForMajorityDurability` used elsewhere) can only resolve once a `cursor` message from another socket updates that node's `lastAckedSeq` - but a `cursor` message arriving after the activation was already enqueued would itself sit queued behind that still-running activation, which is waiting on exactly that cursor to ever arrive. Same class of hazard, same fix, as the replica side's own `prepare_promote` special-case for the identical reason: a message a queued operation may block on waiting for must never be queued behind that same operation.

The queue is also self-healing: each link is wrapped so a message handler that throws (a transient DB error, most plausibly) closes that one connection and logs the failure, but never leaves `primaryMessageQueue` itself in a rejected state - a bare `.then()` chain with no rejection handler would otherwise propagate that failure forward forever, permanently blocking every later queued message until a process restart.

Separately, `revertHaClusterMemberActivation` (used by the durable-confirmation path above) is a primary-mutating write like any other in this codebase, and is gated by the same write barrier (`haPrimaryWriteBarrier`, listed alongside `upsertHaClusterMember`/`deleteHaClusterMember`) - it refuses outright during an active promotion, an authority fence, or a quorum-loss fence, the same as every other configuration write, rather than being able to commit unprotected during exactly the window those fences exist to guard.

That protection alone still leaves a gap worth calling out explicitly, because a third-party review found it: the _original_ activation write and its _compensating_ revert are two separate calls, made several seconds apart (the durability wait sits between them), each independently barrier-protected. A quorum-loss fence engaging partway through that wait - a separate, independently-timed mechanism that can fire at any moment - would correctly have admitted the original write (fence wasn't up yet) but would then just as correctly REFUSE the revert (fence is up now) if confirmation later failed. Refusing the revert is individually correct, but the surrounding code deleted this node from `registeredMembers` regardless of whether the revert it just asked for actually happened - so the database could end up saying a node is active while this primary's own in-memory view said it wasn't, with nothing that would automatically reconcile the two beyond a manual reconnect, restart, or fresh enrollment. The whole write→wait→compensating-revert sequence is therefore now wrapped in a single write-barrier lease, held for its entire duration (up to the wait's own timeout) rather than reacquired at each step, by reusing the barrier's own re-entrancy (an admitted operation's nested repository calls share its lease instead of re-checking the fence - see `runPrimaryWrite`'s own comment). A fence appearing at any point during that window can no longer split the transition into "write admitted, revert refused" - both share the same fate, decided once, at the start. This also means a manual promotion correctly waits for an in-flight activation to resolve one way or the other rather than racing past it, exactly as the write barrier's `beginPromotion` already does for every other admitted write.

For the first upgrade from a release that predates this guard, upgrade the primary first. The upgraded primary learns the older replicas' versions as they announce and turns configuration read-only. Then upgrade and restart each replica; each matching announcement automatically clears its part of the fence, and configuration writes resume as soon as the final registered node matches. On later releases the durable membership already exists, so the fence is active immediately across primary restarts. A join code also carries the issuing primary's exact version and is rejected before enrollment if the joining binary differs, and a mismatched replica cannot be promoted.

## Failover

If the primary goes down, every replica keeps proxying traffic normally - reads are local. Admin writes fail cleanly (503, "the primary is unreachable") until it's back, rather than hanging or silently applying nowhere.

Failover can happen two ways: a human clicking **Promote** on the primary's Cluster tab (below), or - on a cluster of 3 or more registered nodes - an automatic majority-quorum election among the replicas themselves (see [Automatic failover](#automatic-failover)). Below 3 registered members, automatic failover is not just disabled by default, it is mathematically impossible to do safely (a lone replica can never tell "the primary crashed" from "I got network-partitioned away from it"), so a 2-node cluster always relies on manual Promote.

Clicking Promote isn't just a broadcast - it runs a deliberately blocking, durable handoff. The primary stops accepting new admin writes, flushes everything already committed, and captures that point as a barrier sequence. It asks the target to prove it has durably applied every change through that barrier and drained anything still queued to relay. If the target cannot do that, promotion aborts and admin writes resume. Once ready, the old primary persists a node-local promotion intent that also acts as a crash-surviving write fence, then asks only the selected target to activate. The target persists its primary role and epoch first, keeps the current process in replica mode until restart can safely raise its changelog sequence, and acknowledges the exact promotion ID. Only after that acknowledgement does the old primary notify bystanders and atomically persist its own demotion while clearing the durable intent. Consequently a target persistence failure leaves the old primary authoritative, while a crash or ambiguous disconnect during activation leaves the old primary durably fenced and able to resume the same handoff when the target reconnects - it no longer demotes every node before knowing that a replacement primary exists.

If the target never reconnects - it's genuinely gone, or it already came up independently as primary elsewhere and has no reason to dial back into this node - the old primary stays durably fenced with no automatic way out. This is visible, not silent: the Cluster tab shows a banner naming the stuck promotion and its target as soon as nothing is actively trying to resolve it (a fresh attempt or a reconnect-triggered resume both suppress the banner while they're genuinely in progress). There is deliberately no "force clear" button - recovering from this means confirming by hand whether the target really is the new primary and, if so, reconfiguring this node as its replica the same way the manual/by-hand procedure below does; clearing the fence without doing that risks exactly the second-writable-primary split-brain it exists to prevent.

"Stops accepting new admin writes" is an atomic admission barrier, not just a flag checked once near the start of a database method. A whole mutating admin request holds a shared write lease, including requests that call several repository methods; schedulers and direct internal repository mutations take the same lease themselves. Promotion synchronously closes admission and waits for every earlier lease to finish, including its transaction commit, before flushing the changelog and capturing the target's barrier sequence. A new write therefore lands wholly before that sequence or is rejected until promotion finishes - it cannot pass an early check and commit behind the captured barrier.

### Automatic failover

On a cluster of 3 or more registered members, replicas can elect a new primary themselves when the current one disappears, with no human clicking Promote. This is always enabled once a cluster reaches that size; the eligibility floor and safety-critical election/fencing timings are fixed protocol constants, not per-node environment settings. Manual Promote keeps working alongside automatic election and the two are mutually exclusive at any given moment (an election in progress blocks a manual Promote, and vice versa).

**Why 3, and not 2 or "any size":** the safety of an automatic election rests entirely on requiring a strict majority of _all registered members_ (not just whichever ones happen to be reachable right now) to agree before anyone becomes primary. Two disjoint majorities out of the same total always overlap by the pigeonhole principle, so at most one candidate can ever win a given election round - that overlap is what makes it impossible for two nodes to both become primary out of the same vote. With exactly 2 members, though, there is no way to form a majority that excludes the possibility of the other node also thinking it has one (1 out of 2 is a tie, not a majority) - a lone replica that loses its primary connection genuinely cannot tell "the primary is down" from "I am the one who got partitioned away," and no amount of cleverness in the election protocol changes that. `BG_HA_AUTO_FAILOVER_MIN_MEMBERS` is deliberately not an environment variable - it is a fixed constant (3) precisely because making it configurable would let an operator quietly reintroduce that hazard.

**How an election runs**, once a replica has gone without a verified primary connection for longer than its fixed 45-second base election timeout (deliberately conservative, trading a longer writes-down window on a genuine crash for not flapping on a brief network blip):

1. It proposes itself as a candidate for the next cluster epoch (epoch doubles as the election's term number here - it already increases by exactly 1 on every promotion, and now also increases on every election attempt, successful or not) and asks every other registered member for a vote, carrying its own replication cursor.
2. Only a replica that has lost its verified primary connection can vote. A replica still connected to the primary refuses election traffic, and the active primary never grants a vote. An eligible voter grants at most one vote per epoch, persisted to disk _before_ it ever replies (closing the same concurrent-request race the write-fencing barrier above closes, just at the database-row level instead) - and only if the candidate's cursor is at least as caught-up as the voter's own. That log-up-to-date check is a hard safety floor: no candidate can ever win against a voter that knows it holds newer data. It is not, on its own, a guarantee that the _single best_ candidate wins - with a 3-node majority of 2, the most caught-up node isn't guaranteed to be asked before someone else reaches a majority first.
3. To make the best candidate the _likely_ winner anyway (not just a safe one), each node's own election timeout is biased by how far behind it thinks it might be, then by a fixed rank among registered members, with a small amount of random jitter layered on last purely to avoid two equally-positioned nodes starting their campaigns at the exact same instant. Since the primary broadcasts every 500ms, most crashes leave every surviving replica at an identical cursor - so this tie-break, not the log-up-to-date floor, is what actually decides who wins in the common case. It is a heuristic, not a guarantee: under adversarial network timing a less-ideal (but never behind) candidate can still win.
4. Once a candidate collects votes from a majority of all registered members (including itself), it durably persists its own primary role and the new epoch, then restarts into it - the exact same persist-then-restart mechanism the manual Promote target already uses, reused as-is rather than reinvented.
5. There is no old primary left alive to broadcast the change to everyone else (that is the whole premise: it may be genuinely dead, not just demoted) - so the new primary directly notifies every peer it can currently reach, and any node it can't reach right now (offline, or still pointed at the dead address) discovers the new primary itself: whenever its own reconnect attempts keep failing, it asks the other registered members it already knows about "who do you believe is primary right now" and adopts whichever answer carries the highest epoch, using the exact same trust model an ordinary reconnect already uses for a primary reporting a newer epoch.

Each peer certificate lookup and vote request is independently bounded, so an unreachable peer cannot stall a campaign indefinitely. If a round doesn't reach a majority, the candidate abandons that epoch and, if still disconnected, tries again at the next one with a freshly randomized timeout - the same self-correcting retry a partial network split naturally needs.

A campaign is also abandoned if the candidate completes a verified connection to a primary while vote replies are in flight. This is generation-checked, so reconnecting and then disconnecting again before delayed replies arrive still cannot revive the stale result. Election-winner activation and the final verified-connection transition share a synchronous gate: whichever happens first prevents the other, closing the narrow race where a node could otherwise persist itself as primary immediately after proving the existing primary was reachable.

Receiving an authenticated vote request makes the active primary immediately adopt that term and enter a durable temporary election fence: it stops writes, reports unhealthy, and tells its connected replicas that primary authority is temporarily ambiguous. This is deliberately not the sticky stale-authority fence, because a request proves only that a campaign started, not that it won. The election fence remains for at least one full replica heartbeat-liveness window. If a majority keeps acknowledging the primary throughout that window, those connected replicas also refused election votes, proving the campaign could not have won, and the fence clears automatically. If enough replicas disconnect to let a candidate win, their previous acknowledgements expire and the old primary stays fenced - and, per [Automatic former-primary recovery](#automatic-failover) below, automatically attempts to find and adopt the real winner at that same term rather than only ever recovering by way of a missed announcement or manual reconfiguration.

**A fenced primary never answers `who-is-primary` as if it were still authoritative**, whether fenced by a durable authority fence or this election/quorum one - this matters beyond its own recovery: that endpoint is the exact channel a _different_ node's discovery poll and the majority-confirmation check below both trust. A fenced node that kept claiming `role: "primary"` at its own (correct but no-longer-authoritative) epoch would be indistinguishable from a real one to that trust model - a replica that had already correctly adopted the genuine winner could later poll this node, see it self-report as primary at an equal term with a different address, and get pulled back onto stale data through the same path that exists to let a genuinely missed winner announcement be rediscovered. A fenced primary instead reports itself as a replica with no known primary, so it can never be mistaken for - or corroborate - a competing authoritative claim while its own authority is in doubt. A primary mid-promotion (`fencedForPromotion`) is deliberately exempt from this: it's still genuinely authoritative, just temporarily not accepting writes, so it keeps answering as primary.

**A primary that loses touch with a majority of registered members self-fences too**, not just when it directly observes election traffic. Connectivity here means recent bidirectional, application-level heartbeat acknowledgement from a registered node-not merely an open WebSocket, which can remain half-open after a dead host or one-way partition. Replicas acknowledge each heartbeat after reaching its advertised changelog watermark; three missed acknowledgements expire and close that socket before it is used by quorum, status, or promotion logic. After the fixed 10-second quorum-loss grace period, a primary holding less than majority connectivity stops accepting admin writes on its own - without waiting for proof that a replacement has actually taken over elsewhere. The fixed heartbeat, fencing, and election timings guarantee that replicas cannot elect before the old primary's fence. A primary also boots fenced whenever its durable membership is large enough for automatic failover and clears that fence only after re-establishing majority contact, so an isolated stale-primary restart cannot create a writable window. This is what makes the safety argument airtight rather than merely probable: whichever side of any partition still holds a majority is thereby the _only_ side that could ever legitimately hold an election, so it is impossible for a quorum-having primary and a quorum-having election to coexist. Unlike the sticky authority fence described below (which requires a human to reconfigure the node, because another primary may genuinely already exist), this quorum/election fence **clears itself automatically** after safe majority connectivity is established - nothing else could have legitimately become primary while this node held a majority the whole time, so there is nothing to reconcile by hand. Both fences drive `/_burrowgate/health` and the Cluster tab's status the same way.

**The 10-second grace period is measured from when majority was last positively confirmed, not from when a tick first happened to notice it was missing.** That distinction matters for a primary whose process (or its host) is suspended outright - a paused VM, a very long GC pause, a debugger breakpoint - for longer than the grace period: nothing runs during a suspension, including the election tick itself, so a design that started the clock only once a tick actually observed the shortfall would let the very first tick after resuming start a _fresh_ grace period, as if the loss had only just begun, even though majority was genuinely unconfirmed for the entire suspension (long enough for replicas to have already elected a replacement). Anchoring to the last confirmation timestamp instead means that first post-resume tick immediately sees the proof is already stale and fences right away. The same timestamp is also checked directly by the write barrier, independently of whether a tick has run recently enough to have set the fence flag yet - a write should not be able to slip through in the narrow window between a resume and the next tick, only because the periodic timer hasn't had its turn on the event loop yet.

**An accepted, explicit limitation, not an oversight: a write already admitted by the barrier before quorum loss engages is not retroactively cancelled.** The write barrier's admission check (`quorumFenced`, the staleness check above, `authorityFence`, `fencedForPromotion`) runs once, at the moment a request is admitted; an already-in-flight request's own nested repository calls inherit that admission and are not re-checked as they complete, the same re-entrancy the promotion barrier's own draining logic depends on. A sufficiently slow request could therefore still commit in the narrow window between quorum genuinely being lost and this node's own fencing catching up. Closing this would need real transaction-level cancellation of an already-admitted write, not just a stricter admission check - a materially larger, riskier change for a race bounded by ordinary request latency (milliseconds to low single-digit seconds), not the multi-second-to-unbounded windows the mechanisms above close. Deliberately left as-is.

**A replica runs the same half-open check from its own end of the connection.** An open WebSocket to the primary proves nothing on its own - a crashed primary process, a dead host, or a partition that only drops the primary-to-replica direction can all leave the replica's local socket looking healthy indefinitely, with no "close" or "error" event ever firing to tell it otherwise. Readiness already ages out once heartbeats go stale (`BG_HA_MAX_SYNC_STALENESS_SECONDS`), but that alone only stops this node from _serving_ traffic - it does nothing to start the election clock, since `disconnectedDurationMs()` only counts once the connection actually enters the disconnected state. A dedicated watchdog, ticking every heartbeat interval, transitions this replica into the disconnected state itself once no heartbeat has been acknowledged within the same fixed liveness timeout the primary uses to expire a silent replica (three missed 5-second heartbeats) - synchronously, in the same tick that notices the shortfall, not merely by calling the socket's `close()` and waiting for its own asynchronous "close" event to also agree first. That distinction matters specifically for a blackholed connection (packets silently dropped, not a clean reset) - exactly the case this watchdog exists for, and exactly the case where a `close()` call's own event might be delayed or never arrive at all. The watchdog still calls `close()` too, as a best-effort request to actually tear down the socket, but the disconnected/election path no longer waits on it - a replica that would otherwise sit connected-but-deaf forever now reconnects immediately, and if the primary really is gone, becomes eligible to vote or campaign once its election timeout elapses.

Automatic failover shares the same fundamental limit as manual failover: this is still detection plus fail-closed software fencing, not physical fencing. A primary that is fully network-isolated (nothing it can reach, including no path back to a majority) still cannot be stopped externally purely by software running elsewhere - that needs real STONITH-style infrastructure. BurrowGate instead stops it locally after the bounded heartbeat-liveness expiry plus the fixed quorum-loss grace period; that combined bound remains shorter than the earliest permitted election.

If you'd rather do it by hand (or the cluster's already down and the dashboard isn't reachable): **editing `BG_HA_ROLE`/`BG_HA_PRIMARY_URL`/`BG_HA_PRIMARY_ADMIN_URL` and restarting does _not_ work** for this - those env vars only ever seed a node's very first-ever boot (see [Setting it up](#setting-it-up)'s env var table), and every node has already had one by the time you'd need this, since HA is always on. The database row is the only thing that actually matters; edit it directly instead, then restart the process. This bypasses the write-fencing/barrier handshake above entirely (there's no live connection to negotiate it over), so it's on you to be sure the replica you're promoting is actually caught up first:

```sql
-- On the replica you're promoting - cluster_epoch+1 keeps the epoch check below meaningful even
-- for a fully manual failover; skip it and every node just keeps trusting whichever primary it's
-- pointed at, with no detection at all.
UPDATE ha_cluster_config SET role='primary', primary_url=NULL, primary_admin_url=NULL, cluster_epoch=cluster_epoch+1 WHERE id=1;

-- On every OTHER replica, repointing it at the new primary (its shared_token_encrypted stays as-is - it's the same cluster's token) and matching the same new epoch value from above. primary_url is https:, matching BG_HA_PRIMARY_URL's format below - not wss:, even though the mesh itself speaks WSS:
UPDATE ha_cluster_config SET role='replica', primary_url='https://new-primary.internal:7443', primary_admin_url='https://new-primary.internal', cluster_epoch=<the new epoch from above>, authority_fenced=0, authority_fence_epoch=NULL, authority_fence_node_id=NULL, authority_fenced_at=NULL WHERE id=1;
```

If the old primary comes back later and auto-failover is disabled or the cluster is below the eligibility floor, it must be reconfigured with the second statement above (as a replica of the new primary) before rejoining - restarting it still set to `role='primary'` is exactly the split-brain the epoch check below exists to catch, though nothing stops it from still accepting local writes to its own database while it's isolated (see below). In an election-capable cluster, the automatic recovery described next handles this without operator action.

On promotion, the new primary automatically raises its sequence counter past the highest seq it has ever seen (as a primary or as a replica) before issuing anything new, so it never reissues a sequence number some other replica already received from the old primary. Every node also carries a **cluster epoch**, incremented by exactly 1 on every promotion and included in the mesh handshake: a node refuses to trust a primary reporting an epoch older than one it has already seen, rather than silently resuming replication from a node that doesn't know it was demoted. The refusing node sends its authenticated newer epoch back before it stops trusting the stream. On receiving that proof, the stale primary immediately leaves `/_burrowgate/health`, rejects new writes, records a node-local durable authority fence, and advertises the fence to its other replicas. A restart cannot make it writable again.

**Automatic former-primary recovery.** A durably authority-fenced primary **or one that is still quorum/election-fenced with no majority through its own direct connections** does not just sit there waiting for an operator when the cluster is election-capable (`BG_HA_AUTO_FAILOVER_ENABLED` on, and registered membership at or above the automatic-failover floor - the same switch and floor that gate automatic elections). On every election tick it asks every other registered member the same `who-is-primary` question the election discovery-fallback poll uses, and tallies the responses by exact `(epoch, primaryUrl, primaryAdminUrl)` tuple. It only acts once **a majority of all registered members** agree on the identical topology at an epoch equal to or newer than this node's own, **and** at least one of those agreeing responses is the candidate primary confirming its own role at its own registered address - a majority of replicas repeating the same stale or wrong belief is not enough on its own, precisely because it proves nothing about whether that belief is actually correct. Equal epochs are accepted (not just strictly newer ones) because a primary that received a vote request already adopted the candidate's exact term as part of getting quorum-fenced - the genuine winner at that same term is exactly what this needs to find, and requiring a newer epoch would make quorum-fence recovery permanently unable to. This mirrors the majority-of-all-members safety shape a real election already uses, just to corroborate a topology that already exists rather than to elect a new one. Once confirmed, the stale primary atomically demotes itself to a replica of the confirmed primary using the same underlying transition every path that adopts a discovered primary shares (a direct announce-primary push, a primary*redirect, or this recovery path's own majority confirmation) - and that shared transition is what forces a full fresh snapshot on the next connection rather than resuming incremental catch-up, whenever the row it just demoted was itself primary. That check runs atomically, inside the very same database transaction as the demotion - not a separate follow-up step a caller could forget or that could fail independently after the role change already committed, and not something only this one recovery path remembers to ask for. Unlike an ordinary replica being redirected to a different primary (which was never writable, so has nothing to reconcile), a node demoted out of the primary role may have accepted local writes during the split that the confirmed primary never saw; forcing a fresh snapshot replaces its local replicated data wholesale rather than trusting it. That same demotion also wipes this node's own local changelog and resets its high-watermark - a fresh snapshot alone only replaces \_application* tables, and this node's own record of what it broadcast while isolated is not one of those, so it would otherwise survive demotion untouched. Inert while it stays a replica, but if this node is ever promoted again later, a replica whose catch-up cursor happens to fall inside that stale seq range would be served the old, divergent row content still sitting at those seq numbers through the ordinary pull-based catch-up path - which reads the changelog table directly, unconditioned by any broadcast watermark - not just skip past a reserved sequence number, but receive and apply genuinely wrong history. Wiping it here closes that off the same way `joinCluster` already wipes it when leaving one cluster's history behind entirely. It then restarts and rejoins automatically. Below the floor, or with auto-failover disabled, this node stays fenced exactly as described above until reconfigured by hand.

This is still detection plus fail-closed software fencing, not physical fencing. Nothing can stop a completely network-partitioned old primary from continuing to accept local writes before any node with the newer epoch can reach it (that needs real STONITH-style infrastructure this codebase doesn't have). Below the automatic-failover floor, or with it disabled, this epoch-bump procedure is the fully manual, by-hand path with no live connection to negotiate anything over, so - unlike the automatic election and automatic former-primary recovery above, which both have real majority-quorum backing - the Promote button's confirmation dialog (or, here, your own judgment editing the database directly) is still the only thing standing between a safe failover and choosing a genuinely stale replica during a partition.

**A demoted node doesn't just go dark on its old mesh address.** Every replica (including a node that was just demoted) keeps a small, shared-token-authenticated listener on its own `BG_HA_PORT`, whose only job is to answer any incoming mesh connection attempt with a `primary_redirect` message naming the real current primary, then close. This covers a bystander that missed the `promote` broadcast entirely (a dropped connection at the wrong moment) and is still trying to reach the address that used to be primary - instead of failing forever against a now-dead stream endpoint, it learns the new topology directly from the node it mistakenly still trusts and reconnects to the right place. The same listener also answers the automatic election's `who-is-primary`/`announce-primary` HTTP requests (see [Automatic failover](#automatic-failover)) - the mechanisms overlap deliberately: `primary_redirect` only ever helps when the OLD primary is still alive to answer, while the election's own discovery path is what a node relies on when it genuinely isn't.

A multi-writer event (a session, a ban, an identity change) that the primary genuinely cannot apply - not a transient failure, which the originating replica's own timeout-based retry already covers - is dropped rather than retried forever, since with only one such event in flight per node at a time, a stuck one would otherwise block every later event from that same node indefinitely. The primary records what it dropped and why; check the **Cluster** tab's "Dropped replication events" table (or `GET /_burrowgate/api/admin/ha/dead-letters`) if something a user did on a replica doesn't seem to have taken effect elsewhere.

**A permanently rejected relay means more than a dropped outbox row - the local record that produced it is still sitting in that replica's own database, and the primary will never accept it through this path.** Discarding only the outbox entry and moving on (the original behavior) left that row silently and indefinitely diverged - the replica kept serving it as if it were valid cluster state, with no operator-visible signal beyond the primary's own dead-letter table. On a `relay_reject`, the replica now forces a fresh full snapshot on its next connection (the same self-heal repeated apply failures already use) and reconnects immediately rather than waiting for some unrelated future disconnect to trigger it - dropping out of `/_burrowgate/health` right away, the same as any other node now known to be stuck rather than transiently lagging. The snapshot reconciles the diverged row with the primary's authoritative version (or removes it if the primary no longer has it) the same way it already does for every other replicated table.

## Majority-durability confirmation on important writes

Ordinary replication is asynchronous: the primary commits a write locally and returns success immediately, then broadcasts it to replicas on a 500ms timer. That's normally invisible, but it creates a real (if narrow) window - a primary that crashes moments after committing an already-"successful" write, before that write ever reached another node, loses it entirely. Manual Promote already closes this for a planned handoff (it flushes and durably confirms the target caught up before completing), and the automatic-election log-up-to-date check protects rows a majority already _has_ - neither one protects a row that hadn't replicated to anyone yet at the moment of an unplanned crash.

For a bounded set of mutations that directly govern live traffic - sites, origins, route policies and their IP/country/ASN rules, site- and stream-level network policy, firewall sync providers and their whitelist, and the stream equivalents of all of the above - the admin API waits before returning success: after the write commits, it polls (kicking an immediate broadcast rather than waiting out the rest of the 500ms interval) until a majority of all registered members, including the primary itself, have acknowledged reaching at least that write's changelog sequence, or a fixed timeout elapses. **This is not full Raft** - there's no commit protocol or log matching, and the write is never rejected or rolled back on a timeout; it already happened locally. What it changes is only how long the response takes to confirm, and what it confirms: a response carries `durabilityConfirmed: true` once a majority is known to have it, or `durabilityConfirmed: false` if that couldn't be confirmed within the timeout - the dashboard shows a distinct warning toast for the latter rather than an ordinary success message, since the change did save, just without the extra confirmation. This meaningfully narrows the acknowledged-data-loss window without adding a general synchronous-replication cost to every write cluster-wide, and without blocking other, uncovered mutations at all.

Deliberately narrow in two more ways: below the automatic-failover floor, or with the feature disabled, this is a no-op (`durabilityConfirmed: true` immediately) - there's no automatic mechanism that could ever replace a crashed primary in that configuration anyway, so waiting would only add latency with no matching safety benefit. And it only ever runs on the primary; a replica forwards a covered write to the primary and relays its response (including this field) back verbatim, the same way every other admin write already does.

## Verifying it's working

The **Cluster** tab in the dashboard lists every registered node, including offline replicas, by name, role, version, and address - HA is always on, so this list is populated from the moment a node first boots (a cluster of one, until it joins or something joins it). On a replica, the node list transparently asks the primary for the cluster-wide picture rather than showing a locally-cached one - if the primary is unreachable, it says so plainly instead of showing a stale or empty list.

Node connect/disconnect events also fire the existing notification system (see [`docs/NOTIFICATIONS.md`](NOTIFICATIONS.md)) as `HA node down`/`HA node up`, toggleable per-site/stream like any other alert type: the primary reports on a replica it observes disconnect (`warning` severity - redundancy reduced, cluster still serving); a replica reports on losing the primary (`critical` - that specific node can no longer accept admin writes). Neither side tries to learn about a third node's health secondhand - a replica only ever reports on its own link to the primary, not on other replicas it has no direct visibility into.

You can also watch the logs directly:

- Primary: `HA mesh listening on port <port> (primary, TLS)` at startup.
- Replica: `HA replica starting, connecting to primary at <url>`, then (on a first boot with no pinned certificate yet) `HA: fetched and pinned the primary's certificate`, then `HA: connected to primary` once the handshake and initial catch-up succeed.
- A master-key mismatch logs `HA: BG_MASTER_KEY on this node does not match the primary's - refusing to apply replicated changes until it's fixed` and the replica stops applying changes until corrected.
- An application-version mismatch logs `HA: primary and replica versions differ`, makes that replica's health endpoint return `503`, and makes cluster configuration read-only until all registered nodes match.
- A dropped connection logs a warning and retries with exponential backoff; nothing needs to be restarted manually for a transient network blip.
